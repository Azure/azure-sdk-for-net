# ARM provider schema analysis notes

This file tracks the manual root-cause analysis for libraries reviewed after generating the schema comparison reports.

| Library | Status | Root cause / notes | Follow-up |
| --- | --- | --- | --- |
| `Azure.ResourceManager.Advisor` | Good | Legacy and `resolveArmResources` are almost identical. The only requested-axis difference is an extra subscription-scoped `Microsoft.Advisor.ResourceRecommendationBases.list` operation from `resolveArmResources`, and that addition makes sense. | No issue needed. |
| `Azure.ResourceManager.Network` | `resolveArmResources` bug | `resolveArmResources` returns 0 resources while legacy detects 140. Network uses converted/legacy custom resource bases with `@Azure.ResourceManager.Legacy.customAzureResource(#{ isAzureResource: true })`; the ARM resolver does not recognize/register this pattern as resources. Bicep reference validation found the legacy-only resource types are real ARM resources. | Tracked by [Azure/typespec-azure#4798](https://github.com/Azure/typespec-azure/issues/4798). Either fix/enforce the spec pattern or support this custom-resource shape in the library. |
| `Azure.ResourceManager.DevTestLabs` | Resource ID reconstruction mismatch | Raw resource ID mismatches are caused by path variable names (`{name}` vs `{labName}` etc.). The noise is produced because `resolveArmResources` reconstructs the resource ID from resource/operation metadata, while the legacy detector uses the request path from the Read operation directly. After normalizing variables, resource identity, hierarchy, models, and CRUD match. Remaining differences are 2 list/action operation classifications plus 2 extra non-resource methods. | No root-cause issue opened yet; lower priority than real resource identity mismatches. |
| `Azure.ResourceManager.Automation` | Spec modeling issue | Several operations are written as `ArmResourceRead<ParentResource>` even though the response type is not that parent resource, e.g. `nodeCountInformationGet` returns `NodeCounts`, not `AutomationAccount`. `resolveArmResources` promotes those paths to child resources; legacy treats them as actions on the parent. Bicep reference validation found most resolve-only resource types are not real ARM resources; `sourceControlSyncJobs` is the notable real nested resource. | Covered by linter candidates in the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). These should be modeled as actions if the response is not a resource. |
| `Azure.ResourceManager.NetApp` | Version/projection mismatch | `resolveArmResources` detects 9 extra `ActiveDirectoryConfig`/`Elastic*` resources that are decorated with alternating `@added`/`@removed` version ranges. None of their methods are present in the legacy/Tcgc SDK method map and their resolved `apiVersions` are empty, which indicates `resolveArmResources` is seeing resources from the unprojected/full TypeSpec program that are not in the SDK-selected version projection. Bicep reference validation found these are real ARM resources. | Tracked by [Azure/typespec-azure#4800](https://github.com/Azure/typespec-azure/issues/4800). Related to version-aware `resolveArmResources` design work in the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). |
| `Azure.ResourceManager.RecoveryServicesBackup` | Projection/scope mismatch plus operation-result modeling issue | Many operation-result/status endpoints are excluded from C# with `@@scope(..., "!csharp")`, so they do not appear in the saved C# `tspCodeModel.json` or legacy detector output. `resolveArmResources` still sees the full TypeSpec program and promotes these `operationResults`/`operationStatus` paths to child resources because they are modeled as `LegacyOperations.Read<ParentResource>` or similar resource reads. Bicep reference validation is mixed: some operation-result types exist, operation-status types generally do not. There are also singleton paths (`backupconfig/vaultconfig`, `backupstorageconfig/vaultstorageconfig`, `backupEncryptionConfigs/backupResourceEncryptionConfig`) where `resolveArmResources` reports the resource type as only `Microsoft.RecoveryServices/vaults`, unlike legacy; the legacy child resource types are real. | Scope/projection and read-response-shape aspects are covered by the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). Non-default singleton path parsing is tracked by [Azure/typespec-azure#4802](https://github.com/Azure/typespec-azure/issues/4802). |
| `Azure.ResourceManager.TrafficManager` | `resolveArmResources` bug | `resolveArmResources` returns 0 resources and treats all resource operations as non-resource methods, while legacy detects 7 resources. TrafficManager uses converted legacy/custom resource bases (`@Azure.ResourceManager.Legacy.customAzureResource(#{ isAzureResource: true })`) and `LegacyOperations`, similar to Network but smaller. Bicep reference validation found all seven legacy-only resource types are real ARM resources in the package API version (`2024-04-01-preview`). | Same root cause as Network; tracked by [Azure/typespec-azure#4798](https://github.com/Azure/typespec-azure/issues/4798). |
| `Azure.ResourceManager.HDInsight` | Projection/scope mismatch plus action/status modeling issue | `resolveArmResources` detects 6 extra resources such as `clusters/azureasyncoperations`, `clusters/configurations`, `clusters/extensions`, and `clusters/scriptExecutionHistory`. `client.tsp` explicitly says the HDInsight ARM hierarchy has exactly 4 resource types and scopes these operations out of C# with `@@scope(..., "!csharp")`. Bicep reference validation found none of the 6 resolve-only types. A temporary experiment removing `@@scope(Configurations.get, "!csharp")` made the operation visible to the legacy detector, but legacy classified it as an action on `Cluster`, not as a `clusters/configurations` resource. | Covered by the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793): resolver output must honor language scope/projection, and read/action classification must not promote action/status endpoints into resources. |
| `Azure.ResourceManager.Monitor.Workspaces` | Legacy/TCGC projection miss for removed-version resources | `resolveArmResources` detects 6 `healthmodels/*` resources. Bicep reference validation confirms all 6 are real ARM resources in `2025-05-03-preview`, which is one of this package's API versions. However, saved C# `tspCodeModel.json` has no HealthModel/AuthenticationSetting/DiscoveryRule/Entity/Relationship/SignalDefinition clients or methods. The TypeSpec marks those interfaces with `@removed(Versions.v2025_10_03)`, so the C# projection appears to drop them because they are removed in later selected versions, while `resolveArmResources` still sees them from the full program. | Needs separate review: this may be a legacy/TCGC detector miss for a still-valid older package API version, or an intentional SDK projection choice. Related to version-aware resolver/output design in the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). |
| `Azure.ResourceManager.Resources.DeploymentStacks` | Scope representation mismatch | `resolveArmResources` returns six concrete management-group/subscription/resource-group paths in addition to the generic `/{scope}` resources. Bicep confirms the underlying resource types are real in `2025-07-01`, but C# intentionally scopes out the concrete interfaces and exposes generic `DeploymentStacksAtScope` and `DeploymentStacksWhatIfAtScope` resources. Legacy keeps the generic `/{scope}` representation only. | Related to doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793): resolver output needs projection/language-aware filtering or a representation model that does not double-count generic scope resources and their concrete expansions. |
| `Azure.ResourceManager.SecurityCenter` | Mixed singleton/projection and unresolved legacy-only resources | Bicep validation confirms all resource types involved in the coverage mismatch are real in the package API versions. For `advancedThreatProtectionSettings` and `serverVulnerabilityAssessments`, Bicep shows fixed singleton names (`current`/`default`), matching the legacy paths; `resolveArmResources` incorrectly uses parameterized paths. `client.tsp` has C# alternate-type/default-value customizations for those singleton names. `sensitivitySettings/current` and `locations/{ascLocation}` are legacy-only same-version resources and need further review because `resolveArmResources` treats related operations as non-resource methods. | Needs separate follow-up. Singleton/projection aspects relate to [Azure/typespec-azure#4802](https://github.com/Azure/typespec-azure/issues/4802) and the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). |
| `Azure.ResourceManager.FrontDoor` | `resolveArmResources` bug | `resolveArmResources` returns 0 resources and treats all resource operations as non-resource methods, while legacy detects 6 resources. FrontDoor uses converted legacy custom-resource bases marked with `@Azure.ResourceManager.Legacy.customAzureResource(#{ isAzureResource: true })`, e.g. `Resource`, `BasicResource`, and `BasicResourceWithSettableIDName`. Bicep reference validation found all six legacy-only resource types are real ARM resources in the package API version (`2025-11-01`). | Same root cause as Network and TrafficManager; tracked by [Azure/typespec-azure#4798](https://github.com/Azure/typespec-azure/issues/4798). |
| `Azure.ResourceManager.ResilienceManagement` | Legacy/TCGC projection miss for removed-version resources | `resolveArmResources` detects 5 job child/resource types (`chaosJobs`, `chaosJobChildJobs`, `chaosJobResources`, `drillRunChildJobs`, `recoveryChildJobs`). Bicep confirms all 5 are real ARM resources in `2026-03-01-preview`, which is one of this package's API versions. The corresponding TypeSpec interfaces are marked `@removed(Versions.v2026_04_01_preview)`, so the C# projection appears to drop them because they are removed in the latest selected version, while `resolveArmResources` still sees them from the full program. | Same class as Monitor Workspaces. Needs separate review: possible legacy/TCGC miss for a still-valid older package API version, or intentional SDK projection choice. Related to version-aware resolver/output design in the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). |
| `Azure.ResourceManager.Sql` | Mixed legacy/projection/singleton issues | All five coverage-mismatch resource types are real ARM resources in this package's API versions. Legacy-only `firewallRules`/`ipv6FirewallRules` use legacy/custom resource shapes and are attached by `resolveArmResources` as actions on `servers`. Resolve-only `managedDatabaseMoveOperationResults`, `servers/databases/extensions`, and `servers/jobAgents/privateEndpoints` are also real same-version resources and need deeper review. Several same-path resource type differences are non-default singleton `current` paths where `resolveArmResources` collapses to the parent type. | Needs separate follow-up. Likely involves legacy/custom resource handling, projection choices, operation-result/private-endpoint modeling, and non-default singleton parsing ([Azure/typespec-azure#4802](https://github.com/Azure/typespec-azure/issues/4802)). |
| `Azure.ResourceManager.Storage` | Singleton/projection and operation-classification issues | `inventoryPolicies` and `managementPolicies` are singleton resources with fixed name `default` in Bicep, matching legacy. `resolveArmResources` uses parameterized names, so this is a singleton representation bug. `advancedPlatformMetrics` is a real resource but only in `2026-04-01`, outside this package's generated versions (`2025-06-01`, `2025-08-01`), so it is a version/projection mismatch. `immutabilityPolicies/default` and `tables` operation differences are real same-version resources where `resolveArmResources` classifies create/update as parent actions. | Singleton aspect relates to [Azure/typespec-azure#4802](https://github.com/Azure/typespec-azure/issues/4802). Version/projection and operation-classification aspects relate to the doc PR [Azure/typespec-azure#4793](https://github.com/Azure/typespec-azure/pull/4793). |
| `Azure.ResourceManager.CosmosDB` | Mixed real misses and false/projection resources | Three legacy-only soft-deleted SQL resources are real Bicep resources in `2026-04-01-preview`, matching this package and requiring follow-up as possible `resolveArmResources` misses. `cassandraClusters/backups` is real but Bicep currently lists only `2023-03-15-preview`, outside this package's generated versions. `cassandraClusters/commands` is not found in Bicep and is a false-resource candidate or documentation gap. | Needs separate follow-up. Likely involves projection/scope and operation-result/action modeling for Cassandra backup/command endpoints plus a possible `resolveArmResources` miss for soft-deleted resources. |
