# SDK Build Repair

The SDK build repair workflow automatically attempts to repair custom-code build failures in eligible release-planner Auto SDK pull requests. It uses the shared `azsdk tsp client customized-update` engine and commits reviewable changes back to the pull request branch. It does not merge pull requests.

The workflow source is [`.github/workflows/sdk-build-repair.md`](https://github.com/Azure/azure-sdk-for-net/blob/main/.github/workflows/sdk-build-repair.md). The compiled `.lock.yml` file is generated by GitHub Agentic Workflows and should not be edited directly.

## Eligibility and triggers

The workflow only checks out, builds, or repairs pull requests that:

- originate from this repository, not a fork;
- target `main`;
- were opened by `azure-sdk` or `azure-sdk-automation[bot]`; and
- use an `sdkauto/` head branch.

The normal trigger is the `auto-sdk-build-fix` label, which the release pipeline applies to an eligible Auto SDK pull request. A maintainer with write access can request another run by commenting:

```text
/repair-build
```

The manual path rechecks the same eligibility requirements before checking out or building pull request code.

## Enabling and disabling

The repository Actions variable `SDK_BUILD_REPAIR_ENABLED` is the authoritative control. The workflow runs only when its value is exactly `true`.

```bash
# Enable
gh variable set SDK_BUILD_REPAIR_ENABLED --body true

# Disable
gh variable set SDK_BUILD_REPAIR_ENABLED --body false

# Check the current value
gh variable list --json name,value \
  --jq '.[] | select(.name == "SDK_BUILD_REPAIR_ENABLED")'
```

Disabling the variable prevents new repair jobs from starting. Cancel an already-running job separately if it must stop immediately.

## What the workflow changes

The agent:

1. identifies and builds the changed SDK package;
2. passes the build errors to `azsdk tsp client customized-update --edit-scope CustomCode`;
3. repeats only while errors are improving, up to the language-specific limit in `.github/skills/auto-build-repair/repair-config.yml`;
4. commits custom-code fixes and reproducibly regenerated `Generated/` files through a protected safe-output job; and
5. posts one pull request comment describing the result.

The workflow does not edit TypeSpec or other specification inputs, move the pinned commit in `tsp-location.yaml`, change repository infrastructure, or auto-merge. Failures requiring a specification or generator change are reported as out of scope.

## Authentication

The agent uses the workflow's built-in GitHub token with the `copilot-requests: write` permission. The same token is passed to the nested Copilot process used by `azsdk`. No personal access token or repository secret is required.

## Monitoring

List recent runs:

```bash
gh run list --workflow sdk-build-repair.lock.yml --limit 20
```

Watch a run:

```bash
gh run watch <run-id>
```

Inspect its jobs and logs:

```bash
gh run view <run-id>
gh run view <run-id> --log
```

Successful repairs also produce a commit on the pull request branch and an `Auto Build Repair` summary comment. Unsuccessful runs report their stop reason in the pull request comment or workflow logs.

The workflow uses per-pull-request concurrency, so a newer run for the same pull request queues until the in-progress run finishes.
