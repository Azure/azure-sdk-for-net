# SDK Build Repair

The SDK build repair workflow automatically attempts to repair custom-code build failures in eligible release-planner Auto SDK pull requests. It uses the shared `azsdk tsp client customized-update` engine and commits reviewable changes back to the pull request branch. It does not merge pull requests.

The workflow source is [`.github/workflows/sdk-build-repair.md`](https://github.com/Azure/azure-sdk-for-net/blob/main/.github/workflows/sdk-build-repair.md). The compiled `.lock.yml` file is generated by GitHub Agentic Workflows and should not be edited directly.

## Eligibility and triggers

The workflow only checks out, builds, or repairs pull requests that:

- originate from this repository, not a fork;
- target `main`;
- were opened by `azure-sdk` or `azure-sdk-automation[bot]`; and
- use an `sdkauto/` head branch.

The normal trigger is the `auto-sdk-build-fix` label, which the release pipeline applies to an eligible Auto SDK pull request. A maintainer with write access can request another run by commenting:

```text
/repair-build
```

The manual path rechecks the same eligibility requirements before checking out or building pull request code.

## Enabling and disabling

The repository Actions variable `SDK_BUILD_REPAIR_ENABLED` is the authoritative control. The workflow runs only when its value is exactly `true`.

```bash
# Enable
gh variable set SDK_BUILD_REPAIR_ENABLED --body true

# Disable
gh variable set SDK_BUILD_REPAIR_ENABLED --body false

# Check the current value
gh variable list --json name,value \
  --jq '.[] | select(.name == "SDK_BUILD_REPAIR_ENABLED")'
```

Disabling the variable prevents new repair jobs from starting. Cancel an already-running job separately if it must stop immediately.

## What the workflow changes

The agent:

1. identifies and builds the changed SDK package;
2. passes the build errors to `azsdk tsp client customized-update --edit-scope CustomCode` **once**, with `--max-attempts` set to `maxIterations` from `.github/skills/auto-build-repair/repair-config.yml`;
3. lets the engine retry in the same conversation using regeneration/build feedback, without another workflow-side repair loop;
4. commits custom-code fixes and reproducibly regenerated `Generated/` files through a protected safe-output job; and
5. posts one pull request comment describing the result.

The workflow does not edit TypeSpec or other specification inputs, move the pinned commit in `tsp-location.yaml`, change repository infrastructure, or auto-merge. Failures requiring a specification or generator change are reported as out of scope.

The final response is captured as `result.json`. Its `attemptsUsed` counts patch proposals reaching host validation, not tool calls, baseline checks, or JSON files. Failure comments include actual final build/generation diagnostics, attempted edits when known, the stop reason, and next-step guidance. When the final response is missing or invalid, bounded diagnostic details retain the captured stderr first, followed by available final diagnostics and labeled pre-repair build output. A missing attempt count is reported as unknown. Capability and process failures remain failed runs; only failed eligibility checks or a verified green baseline without an engine attempt use a skipped status.

The failure summary uses only the first line of `response_error` and `message`, capped at 500 characters each after Markdown escaping (plus a truncation marker). Detailed engine output stays in the shared 8,000-character diagnostic block so large failure logs do not bypass the reporting limit.

## Engine release dependency

The engine contract from [Azure/azure-sdk-tools#17068](https://github.com/Azure/azure-sdk-tools/pull/17068) is available in [azsdk_0.6.50](https://github.com/Azure/azure-sdk-tools/releases/tag/azsdk_0.6.50), published September 30, 2026. The latest-release installer is unchanged; the skill still checks that CLI help advertises `--max-attempts` and fails closed if unavailable.

The existing workflow eligibility, network/authentication, and native safe-output publisher are unchanged. This does not add independent source receipts, a second validator, or a custom publisher.

## SDK selection and infrastructure failures

`actions/setup-dotnet` installs the exact `sdk.version` from `global.json`, not a
floating `10.0.x` release. Its job-unique installation directory is mounted in the
agent sandbox and exported as `DOTNET_ROOT` and `DOTNET_HOST_PATH`. Only the
approved SDK is installed there; the repository's `rollForward: feature` setting
cannot choose a newer hosted SDK. The baseline helper verifies `dotnet --version`
against `global.json`, and the engine inherits that installation first on PATH
for nested build validation. The repository SDK policy and NuGet feeds are not
modified. This avoids same-day SDK releases introducing implicit ILLink or
ILCompiler packs before they are available through the controlled feed.

The baseline helper records package identity, checkout SHA, raw build output, and
exit code in the writable, secret-redacted agent log directory. Restore and other
baseline infrastructure failures skip the engine. If the agent aborts or emits
only `report_incomplete`, the existing safe-output job renders a failure comment
from this evidence and passes it to the native `add-comment` handler. Missing
engine responses remain `failed` / `NoEngineResult`; no response is invented and
all push requests are removed on recovery. Capability and process failures use
the same fallback. Complete successful output is left unchanged, and a captured
green baseline without an engine attempt retains `skipped_already_green`.

The compiler's empty `{"items":[]}` placeholder is a recoverable output envelope;
an absent `errors` member means no ingestion errors, but a present non-array
member is rejected. Downloaded baseline identity is treated as untrusted:
package paths must be literal `sdk/service/package` paths and checkout SHAs must
be exactly 40 hexadecimal characters before reaching the report's Git commands.
Malformed identity fails visibly without publishing or invoking Git.

The original agent artifact still goes through output validation, so incomplete
and infrastructure failures remain failed Actions runs even when their failure
comment is successfully delivered. If the original artifact cannot be downloaded
or parsed, reporting fails visibly instead of fabricating evidence. Recovered
reports, including full oversized command records, are uploaded as `repair-report`.

## Authentication

The agent uses the workflow's built-in GitHub token with the `copilot-requests: write` permission. The same token is passed to the nested Copilot process used by `azsdk`. No personal access token or repository secret is required.

## Monitoring

List recent runs:

```bash
gh run list --workflow sdk-build-repair.lock.yml --limit 20
```

Watch a run:

```bash
gh run watch <run-id>
```

Inspect its jobs and logs:

```bash
gh run view <run-id>
gh run view <run-id> --log
```

Successful repairs also produce a commit on the pull request branch and an `Auto Build Repair` summary comment. Unsuccessful runs report their stop reason in the pull request comment or workflow logs.

The workflow uses per-pull-request concurrency, so a newer run for the same pull request queues until the in-progress run finishes.

## Maintaining the skill

With Node, PowerShell, and Bash (Git Bash on Windows) available, run the focused checks from the repository root:

```powershell
npm ci --prefix eng\common\scripts\eval
node --test .github\skills\auto-build-repair\test\bounded-invocation.test.cjs
node --test .github\skills\auto-build-repair\test\repair-infrastructure.test.cjs
pwsh -NoProfile -File .github\skills\auto-build-repair\test\emit-repair-report.tests.ps1
pwsh -NoProfile -File .github\skills\auto-build-repair\test\sdk-build-repair-push-gate.tests.ps1
```

The capability eval is `evals/repair.eval.yaml`. It uses the real Copilot executor with a local fixture-backed MCP server, not a real SDK build or publishing service. Regenerate the workflow lock with the repository-compatible `gh aw compile sdk-build-repair` after editing its source.
